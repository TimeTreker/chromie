# Optimize Chromie LLM Prompt

Use the committed Chromie methodology as the authority and this Skill as its
execution entrypoint. Do not duplicate or reinterpret project rules inside a
component prompt.

## Start from project truth

1. Locate the repository root with `git rev-parse --show-toplevel`.
2. Confirm the repository contains
   `docs/LLM_PROMPT_QUALIFICATION_METHOD.md`. If it does not, report that this
   Chromie-specific Skill cannot establish its project authority and ask for the
   correct checkout.
3. Read these files completely before taking task actions:
   - `AGENTS.md`
   - `docs/PROJECT_CHARTER.md`
   - `docs/HUMAN_LIKE_INTERACTION_CONTRACT.md`
   - `docs/STATUS.md`
   - `ROADMAP.md`
   - `DEVELOPMENT_CHECKPOINT.md`
   - `HANDOFF.md`
   - `docs/LLM_PROMPT_QUALIFICATION_METHOD.md`
   - the target role's prompt, context projection, model contract, Schema,
     validator/Host boundary, resolver, and focused tests
4. Inspect `git status --short`, branch, HEAD, upstream, and active Issue.
   Preserve unrelated dirty work.
5. Tell the user that this Skill requires an authority/workflow audit before
   prompt editing. Pause only when a global principle/contract change needs owner
   authorization or destructive/external authority is missing.

The project method document wins if this Skill and the repository disagree.

## Select the task mode

Choose and state one mode:

- **Audit:** inspect the real transaction and report authority, I/O, variants,
  evidence gaps, and proposed corpus without modifying source.
- **Qualify:** freeze and execute a cohort against an unchanged prompt/model
  transaction; do not optimize during the baseline.
- **Optimize:** complete the baseline and diagnosis first, then implement one
  evidenced minimal fix and rerun focused plus full cohorts.
- **Compare models:** hold corpus, prompt, Schema, transport protocol, and
  adjudication constant; change only the declared candidate-model identity.
- **Global change review:** retain the blocker and request explicit project-owner
  authorization before changing identity, worldview, values, semantic authority,
  or a DTO that alters canonical architecture.

Do not infer permission to create Issues, branches, commits, pushes, deployments,
or external reviews. Perform them only when the user authorizes that action.

## Establish the authority contract

Before editing, report:

1. One sentence naming what the model role owns.
2. One sentence naming what it must not own.
3. Every actual invocation variant, including conditional deep cognition,
   streaming/re-entry modes, and permitted mechanical repair.
4. The exact production path:

   ```text
   authoritative upstream DTO/context
     -> global truth projection + role-local prompt
     -> dynamic response Schema
     -> declared model call
     -> raw output -> parser/normalizer
     -> DTO and deterministic Host validation
     -> state transition/downstream owner or fail closed
   ```

5. The evidence claim and maximum evidence level.
6. Any conflict that requires owner authorization.

For each boundary, retain authoritative inputs/material values, actual output,
expected output, correlation/handoff, and a correct/incorrect/unproven verdict.
Do not diagnose from final speech alone or from the static prompt template alone.

## Separate global and local ownership

Classify every proposed change:

- Route global identity, worldview, values, embodiment truth, stable Mind, and
  constitutional authority to their existing canonical owner.
- Route role decision procedure, field meaning, ordering, and examples to the
  existing local prompt owner.
- Route missing/stale/fabricated input to context projection or harness.
- Route unrepresentable valid meaning or admitted forbidden shapes to
  DTO/Schema/validator.
- Route wrong model/options, truncation, timeout, or call mismatch to
  runtime/provider/profile.
- Classify a wrong raw output as model inference only after proving the exact
  prompt, context, Schema, provider, and oracle are sound.

Never hide a global contract gap with local wording.

## Build a frozen contrast corpus

1. Derive cases from the role's production-shaped input, Chromie identity and
   body truth, Goal lifecycle, capabilities, Evidence, Situation, retained
   failures, and bilingual daily life.
2. Store exactly one authoritative scenario per JSON file.
3. Use contrast sets that change one material condition at a time.
4. Keep whole contrast sets inside one split.
5. Declare deterministic invariants, semantic dimensions, acceptable variation,
   forbidden outcomes, and required evidence per case.
6. Keep reference outputs, expected categories, rubrics, and adjudication labels
   out of candidate inference packets.
7. Validate current-contract references through the exact dynamic Schema and Host.
8. Mark valid but unrepresentable cases as known contract gaps.
9. Record counts, language/category/split coverage, provenance,
   `training_eligible=false`, and a deterministic scenario-tree digest.

A generator or combined report may assist execution but must not replace the
separate scenario files as reviewable source truth.

## Run an immutable baseline

Bind and retain:

- source revision and dirty-patch identity;
- complete corpus digest;
- prompt and dynamic-Schema hashes per runtime variant;
- model, role, reasoning/decoding settings, provider/transport, timeout, and
  retry/repair policy;
- target-blind candidate packets.

Run the complete batch without changing source, prompt, Schema, scenarios,
references, or adjudication. Use the model authority selected by the user; never
silently substitute a smaller or local model. Mark interrupted batches incomplete.

Retain per case:

- exact input and rendered prompt identity;
- raw and parsed output;
- transport/termination integrity;
- Schema and DTO/Host verdicts;
- repair attempts;
- semantic verdict and rationale;
- latency and evidence references.

When one model performs both inference and later review, keep the phases separate,
hide targets during inference, and label the result same-model/non-independent.

## Adjudicate and diagnose

Apply evidence in this order:

1. transport and model-call integrity;
2. exact dynamic Schema;
3. DTO and deterministic Host invariants;
4. declared semantic dimensions;
5. aggregate category/language/variant/repair/latency coverage.

Never average a hard safety, provenance, Goal-coverage, capability, execution,
Schema, service-integrity, or safe-idle failure into a pass.

Assign the earliest divergence one primary category:

- `scenario_or_oracle`
- `prompt_or_profile`
- `context_or_harness`
- `contract_or_schema`
- `runtime_or_provider`
- `model_inference`
- `mixed`
- `unresolved`

Distinguish initiating trigger, root cause, downstream symptom, containment,
contributing conditions, and remaining evidence gaps. Cluster failures by the
earliest shared wrong boundary.

## Optimize one evidenced boundary

Select one cluster and one falsifiable hypothesis.

For a local prompt defect:

- place the rule next to the decision it constrains;
- state field ownership and forbidden substitutions;
- remove contradiction or redundancy before adding text;
- prefer a decision procedure and result conditions over phrase examples;
- preserve global truth and upstream/downstream authority;
- keep within the measured context budget.

For a contract defect:

- expose the authoritative invariant at the earliest decoder boundary;
- reject missing meaning before state mutation;
- never make Host or another model invent missing semantics;
- request owner authorization before changing a DTO that alters global authority.

Do not change prompt, model, Schema, context, and oracle together unless evidence
proves one inseparable root cause.

## Prove and stop

After one change:

1. Run focused contract/unit tests.
2. Rerun the exact baseline failure cluster.
3. Verify it changed for the predicted mechanism.
4. Rerun the complete frozen cohort with stable source.
5. Re-adjudicate every case.
6. Compare categories, languages, variants, hard failures, semantic dimensions,
   repair attempts, and latency.
7. Run the applicable general-ability class and canonical repository gates.

Reject a focused improvement that regresses the complete cohort.

Stop when all declared hard gates and semantic requirements pass, no important
slice regresses, no forbidden repair appears, remaining differences are
evidence-classified outside an unresolved prompt boundary, identities/hashes are
retained, and all required gates pass. Do not consume an iteration budget merely
because it exists.

## Apply Planner specialization

When qualifying Planner:

- Treat Fast and Deep as depth passes of one Planner HOW authority.
- Qualify Fast primary/common, streaming advance, and bounded re-entry first.
- Qualify Deep complex, blocked/degraded/unsafe, and revision paths second.
- Rerun both Fast and Deep cohorts after Deep changes.
- Gate complete per-Goal outcomes, Capability/argument contracts, parameter
  provenance, ordering/concurrency, resources, confirmation, safety, truthful
  response text, Evidence scope, satisfaction, unresolved material, revision
  scope, and absence of executable partial leakage.
- Use semantic review for Plan completeness, appropriate Capability choices,
  genuine clarification/escalation/refusal, grounded wording, and whether Deep
  improves complex cases without inventing Work.
- Do not let Deep recovery erase a Fast technical failure.
- Do not let Fast and Deep review or semantically repair each other.
- Prefer acceptable semantic regions plus deterministic invariants over exact
  Plan equality.

## Deliver truthfully

Run the repository-required focused and canonical checks. Record exact commands,
results, prompt/Schema/model/source identities, retained artifact paths, open
blockers, and evidence ceiling in the active Issue.

When the user authorizes commit or push, use the repository delivery-handoff
Skill and include truthful `DEVELOPMENT_CHECKPOINT.md` and `HANDOFF.md` updates
in the same commit. Exclude unrelated user work and never claim deployed, voice,
simulator, physical robot, safety, or release evidence from offline inference.
